## P05 — Use cases and statechart → service layer

**Model used:** `models/use-cases.jpg` and `models/bloodpack-statechart.jpg` 
**Generator:** DeepSeek
**Accepted output:** `prompts-output/P05-output.md`
**Related:** `round-trips/round-trip3-P05.md`

This is the first step where the models drive behaviour rather than structure. The use case
diagram says what the system does; the statechart says which state changes are allowed. Both
were handed over as pictures, with the statechart named as the authority on transitions.


#### Prompt

> Attached is bloodpack statechart, a statechart showing every state a blood pack can be in and every transition allowed between them. Also attached use-cases model, that shows the use cases the system supports.
> Illustrate how to structure the service layer on top of these DAOs, consider the following requirements:
> cover the use cases shown in the use case diagram, grouped as:
> DonationService, InventoryService, TransfusionService
> A blood pack may only move between states along a transition shown there, and the guards on those transitions are the conditions under which each use case changes a pack's state;
> BloodPackState no longer has a RESERVED value, remove it, as the statechart shows;

> Where a use case needs a rule about the domain itself (blood type compatibility, whether a pack has expired, whether a state change is allowed) put that rule on the domain classes rather than in the service, and return those classes in full as well;
> If a use case needs a query that BaseDao does not provide, add it to the relevant DAO;

> Return every class in full.

### Issues detected and asked to modify

| # | Issue | Correction requested |
|---|---|---|
| 1 | `BloodPack` left a public `setState()` method open, allowing outside code to bypass safety rules and change states directly. | Remove `setState` with no replacement; all state changes go through the transition methods. |
| 2 | `markTransfused()` set blood packs to `DISCARDED`, making it impossible to distinguish transfused blood from wasted blood. | Add a `TRANSFUSED` state and set it. Requires a change to the statechart first; see Round trip #3. |
| 3 | `recordDonation` created only one `BloodPack`, treating a one-to-many relationship (`Donation 1 — * BloodPack`) as a one-to-one link. | Update the method to generate and save all blood packs produced by the donation. |
| 4 | `recordScreeningResult` updated only a single pack, leaving any other packs from the same donation stuck in `QUARANTINED` forever. | Accept a donation ID instead, updating the screening result for the whole donation and all of its associated packs together. |

Issue 1 was declared by the generator itself, it
noted that `setState` remained even though state changes were meant to go through the
transition methods, and that it had not been asked to remove it. Issue 2 was likewise
declared, correctly identified as a gap in the statechart rather than an error in the code.

### Decisions made by the generator, accepted

- Blood type compatibility placed on `BloodType.canDonateTo(BloodType)`, with
  `BloodPack.isCompatibleWith(Patient)` navigating from pack to donation to donor. The rule
  sits on the domain classes, as asked.
- Expiry expressed as `BloodPack.isExpired()`, and the two conditions combined in
  `canBeIssued()`.
- One guarded method per transition — `markAvailable`, `issue`, `returnToAvailable`,
  `discard`, `markTransfused`, each throwing `IllegalStateException` when called from a state
  the statechart does not allow.
- `BloodPackDao.findByStorageLocation` added. The use case "list packs in location" 
  needs it and `BaseDao` does not provide it.
- `IllegalArgumentException` for not-found and `IllegalStateException` for invalid state. No
  custom exception types were requested.
