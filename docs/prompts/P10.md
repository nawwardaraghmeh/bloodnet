## P10 — Read endpoint

**Model used:** `models/round-trip4-use-cases.jpg` (updated)
**Generator:** DeepSeek
**Accepted output:** `prompts-output/P10-output.md`
**Triggered by:** `prompts/P10.md` first attempt, `round-trips/round-trip4-P09.md`

This step exists only because the test generation in P09 could not be completed. It was not in
the plan: the API had been generated from a use case diagram of six commands and one
list, and nothing had revealed the omission until a client with no access other than HTTP was
pointed at it.

### Model change made first

One use case, **View blood pack**, added inside the system boundary and linked to the
Storage Operator, and the diagram re-exported. 

### Prompt

> The use case diagram has been updated with one new use case, "View blood pack". Two additions. Return in full only the classes that change.
> add a use case to InventoryService that returns a single blood pack by its identifier, and expose it as GET /inventory/blood-packs/{packId} returning a BloodPackResponse. a pack that does not exist is a not-found failure, signalled the same way the existing services signal one.
> donationResponse carries the codes of the packs produced by a donation but not their identifiers, so a client that records a donation cannot afterwards refer to those packs. Add their identifiers.

> Change nothing else.


### Decisions made by the generator, accepted

- **`packIds` added alongside `packCodes` rather than replacing it.** The instruction was to
  add the identifiers and change nothing else; removing an existing field would have been a
  change.
- **The same `IllegalArgumentException` used for a missing pack** as everywhere else, so the
  exception mapper added at P07 turns it into a 404 with no further work.
- **No change to `BloodPackDao`.** `find(Long)` inherited from `BaseDao` was already enough,
  so the read endpoint required no new query, the generic DAO from P04 absorbed a requirement
  that arrived six steps later.
