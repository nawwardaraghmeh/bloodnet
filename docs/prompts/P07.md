## P07 — REST error handling

**Generator:** DeepSeek
**Accepted output:** `prompts-output/P07-output.md`

Until this step, every rejected operation reached the client as HTTP 500 with a stack trace.

### Prompt

> Write the exception handling for the REST layer using Jakarta REST, so that:
> a not-found failure returns 404 and a not-allowed failure returns 409;
> the response body is JSON carrying the failure message and nothing else, no stack trace, no exception class names, no internal paths;
> the handling lives entirely in the REST layer: the services and the controllers are not changed;

### Issues detected and asked to modify

None. Two `@Provider` classes implementing `ExceptionMapper`, one `ErrorResponse` record, no
change to any service or controller, and no catch-all mapper that would have swallowed real
bugs.

### Decisions made by the generator, accepted

- One mapper per exception type rather than a single mapper testing types with `instanceof`.
- `ErrorResponse` carries only `message`, with no error code, no timestamp and no path.
- No `ExceptionMapper<Throwable>`, so anything unexpected still surfaces as 500 rather than
  being disguised as a business failure.
