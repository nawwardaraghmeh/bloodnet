`@QuarkusTest` with JUnit 5 and RestAssured. The test drives the application over HTTP with

JPA mapping and the domain rules.

### Prompt

> Write end-to-end tests that exercise the system through its HTTP endpoints, using @QuarkusTest with JUnit 5 and RestAssured. Consider the following requirements:
> one test walks the whole system in order: register a donor, register a patient, register a storage location, record a donation producing two packs, record a passing screening result, place a pack into storage, list the packs in that location, issue a pack to the patient, and record the outcome as transfused. each step must take the identifiers it needs from the response bodies of the earlier steps, never from hard-coded values, and the state of the pack must be asserted after every step that changes it.
> further tests cover the failures the system is meant to refuse: recording a screening result for a donation that does not exist (404), recording a screening result twice for the same donation (409), issuing a pack that is not available (409), and issuing a pack to a patient whose blood type cannot receive it (409). each of these tests creates the data it needs

> nothing should reach the application except through HTTP: no DAO, no service and no EntityManager in the test code

### First attempt; blocked by the system, not by the generator

The generator could not write the tests and said why. It produced the walkthrough and the
four failure tests, then reached a helper it could not implement, and gave this instead:

```java
private long getFirstPackId(long donationId) {
    throw new UnsupportedOperationException(
            "This helper requires a GET /collection/donations/{id} endpoint "
            + "or a donation response that includes pack IDs. "
            + "See the decisions section for the required API additions.");
}
```

Its own decisions list stated the two gaps:

- The test assumed `DonationResponse` would return database `packIds`, which are required by later API calls to store or issue a blood pack. Because the response currently returns only business `packCodes`, the full HTTP test workflow cannot continue.

- Assumed a `GET /inventory/blood-packs/{packId}` endpoint exists. The test needs to verify how a blood pack's state changes after each step. Without a specific endpoint to look up an individual pack by its ID, those state checks cannot be performed using HTTP calls alone.

The cause is traceable to the use case diagram, which lists six things people do (record,
screen, place, issue, record outcome, list) and the REST layer was generated from
exactly those. Nobody had said "look at a pack", so nothing could.

This is the only step in the whole build where the failure was in the system rather than in
the generated code. Everywhere else the generator got something wrong; here it got the task
right and reported that the task was impossible.

### Decisions made by the generator, accepted

- **Distinct business keys in every test** — `D1`–`D4`, `P1`–`P4`, `PACK1`–`PACK6`; so no test
  can collide with another on the unique constraints.
- **`expiresAt` set to 2099** in the shared donation helper, so that no test can be rejected
  for expiry when it is meant to be rejected for something else.
- **Screening recorded before the incompatibility test**, with an explicit assertion that the
  pack is `AVAILABLE` first; otherwise the issue would have been refused for the wrong reason
  and the test would have passed without testing anything.
- **No screening in the not-available test**, leaving the pack in `QUARANTINED` so the refusal
  is unambiguously the one under test.
- **Only the presence of `message` asserted on failures**, not its wording, so the tests do not
  break when an error message is reworded.
